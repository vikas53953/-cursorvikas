The panel's direction is right. One option has a hole, and the stack is bigger than it needs to be.

Verdict on the six options, reasoned from one principle: the voice AI hallucinates because it currently holds authority over facts. The fix is to move that authority into the deterministic engine — once — not to constrain the AI's behavior case by case.

Verdict — agree, with one amendment

Adopt O1 + O3 + O6 as a single contract. O5 is its return values, not a layer. Defer O4. Skip O2.

The panel's layering is sound and genuinely general — no per-case rules anywhere. But O1 as written does not kill Bug 1: "switch 99 → VLAN 99" happened before any tool was called, so a lock on the tool validates the AI's paraphrase, not your words. Amend O1 so the resolver receives the user's verbatim phrase, and the whole plan collapses into one clean structural change instead of five layers.

The hole in O1

Replay the real failure against the lock. Every gate passes — because the substitution happened inside the model, upstream of everything the lock can see.

"Switch 99" never reaches the catalog

You"What's on switch 99?"
Voice AIreinterprets → device: sw1, command: show vlan id 99← substitution happens here

The lock checked the wrong input. It can only validate what the model chose to ask about — and the model already swapped the entity. The general fix isn't a stronger lock; it's changing whose words get resolved. The Realtime API already gives you the user's transcript. Make the tool contract carry the user's verbatim target phrase ("switch 99"), and let the deterministic resolver — the same one chat uses — map phrase → device. The model's only job on the way in is to quote you, not interpret you. Then "switch 99" hits the catalog, matches nothing, and the only possible reply is the honest one. This also handles mishearing for free: a misheard phrase resolves to not-found or ambiguous, and the ladder answers honestly — ASR noise gets caught in the right place, deterministically.

What to actually build: one grounded tool

O1 (amended) + O3 + O5 are one contract, not three features. O6 is the conversational wrapper around it. Concretely: one tool spec in tools.cjs, a compose step on top of the query layer you already shipped in Phase 1, and persona rules.

ask_network( target_phrase, question )

The model passes your words through untouched; the engine does everything that must be true.

1 · Quotemodel sends your verbatim phrase — "switch 99" — never its guess → 2 · Resolveexisting query layer: found / ambiguous(candidates) / not-found → 3 · Executeread-only, capped, real devices only — already built → 4 · Composeengine returns the sentence: "sw1 is running 17.9.4" → 5 · Voicemodel speaks it, wrapped in the two-beat hedge
  • One sentence replaces 100,000 rules: "You may not state any network fact you did not receive from the engine." Rules constrain choices and grow with cases; this removes the choice and stays constant.
  • Honesty is structural, not behavioral: for a device that doesn't exist there is no fact to hand over — the only sentence the engine can return is "there's no switch 99." The model can't improvise what it never receives.
  • Pin the anaphora in the contract: the engine tracks the last confirmed device, so "and its uptime?" resolves deterministically too — not by the model's memory.

Why this won't repeat the July 4 revert

The reverted attempt and this design are different species, even though both "route voice through the engine."

Reverted — engine replaced the voice

Transcribe → run engine → synthesize speech. A serial pipeline where the speech model was swapped out as the conversational surface. Nothing could speak until the whole chain finished — hence the latency, and an orb with no live audio session to animate against.

This — engine serves the voice

The speech-to-speech model stays the surface: it hears you, speaks the instant hedge ("checking sw1…"), and calls the engine as a tool mid-turn — the exact mechanism voice uses in production today. The orb never stops because the speaker never stops. Only the fact waits; the ~1s wait hides under the hedge.

Residual risks — named, not hidden

The model could still ignore the sentence

No prompt makes a probabilistic model 100% obedient. Two mitigations: the contract gives it nothing else to read (the engine returns the sentence, not raw output to dig through), and deferred O4 runs as telemetry to measure compliance instead of assuming it. If logs show drift, promote O4 to active.

Composed answers could sound robotic

Real risk, cosmetic severity. The model may own tone and lead-ins ("looks like…") — just not facts. Broad questions ("how's my network?") need a summary compose mode; that's a compose-step feature, not a new architecture.
