Grounded answers · Intent→command · Independent verdict · Fable 5 · 2026-07-06

You're both right — about two different jobs. The AI translates. The engine referees.

The owner is right that translation is knowledge work and belongs to the AI — a hand-written intent→command map is the per-case anti-pattern and never ends. The engineer is right that something deterministic must stand between the AI's output and a real switch. The mistake is thinking those are the same job. They aren't: one is knowing, the other is checking — and checking is one grammar rule, not 100,000 cases.

Verdict

AI owns intent→command. Engine owns a syntax gate + one retry loop. No map — but keep an earned cache.

Give the tool a dedicated ios_commands field whose contract says "exact CLI syntax, never the user's sentence." Engine-side, add one general register check (is this CLI or English?) in front of the existing read-only gate; on rejection, bounce a corrective error back so the model fixes itself in one round-trip. If the voice model can't produce a command, the engine asks the strong text model (GPT-5.x — the chatCompletion path you already run) to form it. Every answer names the command it ran. The only "canonical set" allowed is a cache the system earns from commands that succeeded live — no human ever writes an entry.

Why it failed — the gate checked safety, not syntax

Verified in the live code, not guessed. This was a contract failure, not a knowledge failure: the model didn't send a wrong command — it sent no command.

Three things lined up. First, the whole grounding persona drills "verbatim, verbatim, verbatim" — quote the engineer, never paraphrase. That discipline is exactly right for target_phrase and exactly wrong for commands, and the contract never states the asymmetry. The model obeyed its strongest instruction in the wrong register. Second, the read-only policy checks safety — first word allowed, no mutating tokens — and an English sentence that happens to start with "show" is genuinely safe. It sailed through because no layer owns well-formedness. Third, the speech model is optimized for latency, not discipline; given a loosely-typed free-text field, it took the path of least resistance.

The ChatGPT comparison cuts the other way. When you ask ChatGPT for a command, there's a validator in the loop: you — a 15-year engineer who eyeballs the command before typing it into a real box. NetJarvis removed the human but kept only the knowledge half of that loop. The fix is not less AI; it's restoring the missing half — a referee between the proposal and the device.

The five questions, answered

Q1

Should the AI own intent→command translation?

Yes — with a referee

Yes. IOS command knowledge lives in the models, is vast, and shifts across platforms and versions — encoding it engine-side is per-case forever, exactly the anti-pattern the owner rejects. But "the AI should know" is a capability, not a reliability mechanism. The enterprise pattern is AI proposes, engine disposes: the model translates; a deterministic gate verifies form and safety before anything touches copper. That gate is general — one grammar question ("is this CLI syntax?"), not one rule per command.

Q2

How do we make it reliable?

Contract first, model second

1 · Type the field. Split the registers explicitly: target_phrase = the engineer's words, verbatim (engine resolves). ios_commands = the AI's expert translation, exact CLI syntax, described in the spec as "never natural language — if unsure of exact syntax, omit it." The asymmetry stated once, in the contract, fixes the class.

2 · One register gate, engine-side. Before the read-only check: reject any "command" that reads as English rather than CLI — interrogatives, pronouns, politeness words, a question mark, or the device name inside the command (targeting is the engine's argument, so "…on sw1" inside a command is malformed by definition). That's a language-register test, not an intent map — it catches every possible sentence without knowing any command's meaning.

3 · Corrective bounce, not silent failure. On rejection the engine returns: "not valid IOS-XE syntax — send the exact CLI command only." The model self-corrects in one round-trip, hidden under the two-beat hedge. Same bounce on a device "% Invalid input", once.

4 · Strong-model fallback. Was the model too small? Partly — but don't move command formation wholesale to GPT-5.x (latency). Fast path: the realtime model proposes, free. Fallback: if the gate rejects twice or the model omits commands (need_command), the engine asks the strong text model to form the command from the verbatim question, validates it, runs it. Reliability from a better knower — still zero maps.

Q3

Safe and honest?

Safety is solid — add the echo

Safety already held. The executors enforce read-only at the last mile (allowed first verb + blocklist), which is why the failure was an ugly error, not a dangerous one. Keep that layer exactly where it is — at the executor, so no future path can bypass it.

Honesty gap is real but cheap to close: echo the command. A wrong-but-valid command ("show vlan brief" when you asked for MAC table) returns real-but-wrong output — the one failure no gate catches. Rule: every CLI answer names its command, spoken briefly and shown in the panel: "From show mac address-table on sw1: …". A network engineer catches a mismatch instantly, at zero latency. Extend the existing silent fact-audit telemetry to log question-vs-command pairs. Active semantic read-back (a second model judging the command) is overkill today — same posture as the deferred second-checker: telemetry first, promote only if the logs prove drift.

Q4

Any role for a canonical command set?

Not as a mechanism — yes as an earned cache

The owner is right to reject a hand-written map as the translation mechanism. But don't ban two things that only look similar. (a) An earned cache: when a translation passes the gate and the device accepts it, the engine may remember that question-shape → command pair and reuse it. No human writes entries; it grows from live, device-validated usage; it's a latency win on the top-20 voice questions. Caching verified answers is fixing the class — refusing it on principle would be rejecting the pattern, not the anti-pattern. (b) Eval fixtures: a small test list to score translation accuracy per model, so "the AI knows IOS" becomes a measured number instead of a belief. Neither is a rulebook in the answer path.

Q5

Where's the clean line with shipped grounding?

Truth vs. understanding

One sentence covers everything shipped and everything proposed: the engine owns whatever must be TRUE; the AI owns whatever must be UNDERSTOOD. True: which device exists, whether a string is well-formed read-only CLI, what the device actually printed, what the composed fact is. Understood: what the engineer meant, which command expresses that intent, how to phrase the spoken answer. Device resolution already follows this line (AI quotes, engine resolves). Command translation sits on the border and splits the same way: the AI proposes meaning, the engine verifies form. Nothing shipped changes; this fills the one box that was empty.

The shape to build

One field, one gate, one bounce, one fallback. Everything else is already live.

ask_network( target_phrase, question, ios_commands? )

Fast path stays fast — the gate is microseconds and the bounce only fires on a bad proposal, hidden under the "one sec, pulling sw1…" hedge.

  • The class-level rule, stated once: "target_phrase is always the engineer's words; ios_commands is never the engineer's words." Two registers, one sentence — it covers every question ever asked.
  • The gate never knows what a command means. It only knows what a command looks like. That's why it's not per-case: it rejects any English sentence, including ones nobody has thought of yet.
  • Earned cache sits beside the flow, not in front of the AI: device-validated pairs get reused for latency; a cache miss just means the normal path runs.

  • Intent — what the engineer is actually asking
  • Translation — which exact IOS command expresses it (this proposal: AI-owned, engine-refereed)
  • Summarizing — reading raw CLI output back in plain language, numbers only from the output
  • Voice — tone, lead-ins, the two-beat hedge

Residual risks — named

A valid-but-wrong command survives every gate

No syntax check can know you wanted MAC, not VLAN. Mitigation is the echo (instant human catch, zero latency) plus telemetry to measure how often it actually happens before building anything heavier. If the logs show real drift, the GPT-5.x fallback path doubles as an async auditor later.

The bounce costs a round-trip on a bad first try

Roughly a second, and only on failures — the hedge line covers it. If evals show the realtime model failing the gate often, flip the default: engine always forms table-question commands via the strong model, voice model never tries. That's a dial you can turn from data, not a redesign.
