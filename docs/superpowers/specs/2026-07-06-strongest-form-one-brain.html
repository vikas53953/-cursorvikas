Verdict — the strongest form

One brain, two mouths. The voice model stops deciding anything. The referee uses Cisco's own grammar. And "strongest" becomes a number you measure, not a belief.

Your chat agents work because a strong text model with full attention does the thinking. Your voice agent failed because a speech model optimized for sound was asked to think. So stop patching the weak thinker — remove thinking from the mouth entirely. Voice and chat share one grounded brain (the one that already works); the speech model only hears, hedges, and speaks. My previous design kept the voice model as decision-maker with a referee behind it. The strongest form makes it not a decision-maker at all — my "fallback" becomes the default, and the whole class of voice-only intelligence bugs disappears, because voice no longer has separate intelligence.

The clue you handed me

"Many have built this, I have built this, chat-based, and it works fine." Correct — and here is why it works fine, which tells us exactly what to copy and what to throw away.

Your chat bots never had this bug for three structural reasons — none of them is "chat is easier"

ThinkerChat: a frontier text model forms the command with full deliberate attention. Voice today: gpt-realtime — a model whose training budget went to sounding human, forms it while streaming audio.
InputChat: clean typed text. Voice: ASR output with mishearings — which your device-resolution engine already absorbs. The input problem is solved; the thinker problem isn't.
PatienceChat: three seconds is fine, so the strong thinker fits. Voice: you assumed it doesn't fit — but your two-beat hedge exists precisely to buy those seconds. You already built the patience.

Conclusion from first principles: voice didn't fail because voice is harder. It failed because the intelligence was placed in the weakest model in the chain. The fix is not to coach that model harder (my last page) — it's to move the intelligence to where it already works and keep only the sound. Same lesson as the device bug, one level up: you didn't teach the voice model your inventory; you took inventory away from it. Now take commands away from it too.

The architecture: one brain, two mouths

Nothing here is the July-4 revert. The speech-to-speech model stays the audio surface — orb alive, hedge instant, mid-turn tool call, exactly the mechanism running in production today. What changes is only what's inside the one tool it calls.

Mouths speak. The brain knows.

Mouth 2 · Chat (already live)Same brain, typed in and typed out. Your proven pipeline — this is the part you told me already works without issue. It becomes the only pipeline.

  • Why this is the ceiling: every factual decision now happens in a deterministic engine or the strongest available reasoning model — never in a speech model. There is no weaker link left to move intelligence out of.
  • Latency, honestly: the think step costs ~1–2s over the voice model deciding alone. The hedge was built for exactly this gap, and the fast lane means the most common questions never pay it. The earned cache (validated question→command pairs) shrinks it further with use. In a NOC, a right answer at 3s beats a wrong one at 1s every single time.
  • Enterprise dividend: one brain is one audit trail, one permission model, one eval score — the shape a bank actually certifies. Two brains is two certifications and a diff between them.

What I looked for beyond this — and why I'm not recommending it

Constrained decoding (grammar-locked generation)

Force the model to emit tokens only from a CLI grammar, so a malformed command can't be generated at all. Genuinely stronger in theory; in practice the legit-reads referee catches the same class post-hoc for a fraction of the effort. Revisit if evals ever show valid-syntax-wrong-command drift. Structured JSON output for the think step, though — take that for free.

Second-model verification of every answer

A judge model re-checking each spoken answer against raw output. Doubles cost and latency for a failure mode the echo + telemetry already surfaces. Telemetry first; promote only on evidence — the same discipline that kept O4 deferred.

Bottom line

Build order for the strongest form: ① point voice's one tool at the chat brain for command-shaped questions (the code exists on both sides; this is wiring, not building) → ② fetch Command Runner's legal-command list and make it the referee (verify the legit-reads endpoint against the sandbox first — one API call) → ③ freeze your live test questions into a replay set and score every future change against it. After that, "is this the strongest?" stops being a question you ask a model — it's a number on your own dashboard, and it goes up every time a better model ships.
