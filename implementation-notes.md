## SME review fixes (post-build hardening)

- **Fix 1a (precedence, `electron/core/grounding.cjs`):** moved the `commands`-array branch above the `composeFact(...)` call. Previously a caller-supplied `commands` array was computed but never consulted until *after* a fact match had already returned — since Fix 1b (below) had not landed yet, an over-broad synonym match could return a wrong "fact" and the commands were silently discarded. Now: commands non-empty → CLI/output path runs and returns immediately; single-fact composition is only attempted when no commands were supplied. This is a pure reordering, no new logic.
- **Fix 1b (attribute-guard, `electron/core/fact-compose.cjs`):** removed the ambiguous bare synonyms (`address`, `status`, `running`, `code`) from the attribute map — they were plain English words that also appear in ordinary CLI/table questions, not names for the extracted device field. Kept only unambiguous heads (`ip`/`ip address`/`management ip`, `version`/`software`/`ios`, `uptime`, `model`/`platform`/`hardware`, `serial(...)`, `role`, `reachability`/`reachable`, `cpu`, `memory`/`mem`). Added one general guard at the top of `composeFact`: if the question contains a CLI/table signal word (`show`, or an L2/L3 table noun: `vlan`, `mac`, `arp`, `route`/`routing`, `interface`, `spanning`/`stp`, `cdp`, `lldp`, `bgp`, `ospf`, `neighbor`, `counter`, `logging`) it returns `{matched:false}` unconditionally, before attribute detection runs at all. **Judgment call:** I did not special-case "reachability"/"reachable" against `interface` even though "is sw1's uplink interface reachable" is plausible phrasing — the guard fires on any table noun including `interface`, so that phrasing now falls through to CLI (need_command), which is conservative and matches the stated class rule ("single facts = inventory attributes only"); a true single-device reachability question just says "is sw1 reachable" with no table noun and is unaffected (test coverage confirms this still resolves).
- **Fix 2 (anaphora on the command path, `electron/core/grounding.cjs`):** the CLI/output branch now calls `queryLayer.run(device.name, commands)` (the device the engine just resolved from `resolveScope`) instead of the raw `targetPhrase`. `targetPhrase` can be a bare pronoun ("its") that resolves to nothing when run directly against the query layer's own name-matching. `device.name` is always a real resolved device name at that point in the function (the `resolved.total === 0` branch already returned earlier). Existing test ("non-fact question with commands runs queryLayer and returns output") still passes unchanged because in that fixture `targetPhrase === device.name === "sw1"` already — no observable behavior change for the non-pronoun case.
- **Fix 3 (scoped mandatory rule, `electron/tools.cjs` `JARVIS_INSTRUCTIONS` + `electron/answer-policy.cjs` `squadChatSystemAppendix`):** reworded "ANY question about a device or anything on the network" → "any question about a SPECIFIC NAMED DEVICE OR TARGET", and added an explicit exemption line naming the four fleet-wide tools (`network_overview`, `network_inventory`, `topology_show`, `active_alerts`/`overnight_events`) so the model doesn't route "how is my network doing" through `ask_network` and hit `not_found`. **Judgment call:** these are LLM system-prompt strings with no existing test coverage (no test file previously asserted on `JARVIS_INSTRUCTIONS` or `squadChatSystemAppendix` text). Added `test/mandatory-rule-scope.test.cjs` as a lightweight regression guard — it asserts the new scoped phrase is present, the old over-broad phrase is gone, and the exemption line names all four tools, in both the voice and chat prompt strings. This can't verify actual LLM routing behavior (that would require a live/eval harness), only that the instruction text itself was changed as intended and won't silently regress back to the over-broad wording.

New tests added: `test/fact-compose.test.cjs` (+6 CLI/table-guard regression cases), `test/grounding.test.cjs` (+2: commands-not-dropped, anaphora-on-command-path), `test/mandatory-rule-scope.test.cjs` (new file, +4 cases for the scoped-rule prompt text). `npm test` (93/93) and `npm run typecheck` both green after all three fixes.

  - **Judgment call (the plan's own caveat):** the plan flags that a natural-language echo like `"show me the mac address table on sw1"` starts with "show" and only contains word/space characters, so the tight shape regex `^(show|sh)\b[\w .:|/*-]+$` alone would NOT reject it, and `assertReadOnly` also would not reject it (no blocked token). Implemented the plan's own prescribed fourth guard: reject any candidate containing a whole-word filler token (`me|the|please|what|is|are|on|of`) via `\b(...)\b` — a real IOS show command never contains these words. All four guards ((a) shape, (b) first word ∈ legitVerbs, (c) assertReadOnly, (d) no filler words) must pass; invalid candidates are dropped, not replaced. If zero candidates survive, returns `{ok:false, error}` — never throws, never fabricates a command.
